# 今日、誰としゃべった？

ひとことの会話を、季節の花で振り返るスマートフォン向けPWAです。HTML / CSS / Vanilla JavaScriptのPWAです。端末内保存はログイン不要で、クラウド同期には同梱の公式Supabaseクライアントを使用します。人物情報と日付は端末内のIndexedDBに保存します。

## 起動・ローカル開発

Node.js 20以上で、このフォルダを開いて実行します。

```sh
npm run dev
```

http://127.0.0.1:4173 を開きます。HTMLを直接ダブルクリックする `file://` ではES Modules・Service Workerが動作しないため、ローカルHTTP配信が必要です。開発サーバーはPC自身だけに接続を許可しています。

```sh
npm install
npm test
npm run build
```

`npm install` は公式Supabaseクライアント、ビルド用esbuild、テスト用fake-indexeddb・PGliteを追加します。`dist/` が配信用の静的ファイルです。任意のHTTPS静的ホスティングにこの中身を配置できます。実行時サーバーロジックはありません。Sitesの非公開プレビューにはホスト側の閲覧認証がありますが、アプリ自身には認証処理はありません。ログイン不要の一般利用にはHTTPS静的ホスティングを使用してください。

## PWA確認方法

1. HTTPSで配信したURLをiPhone Safariで開きます。PCではlocalhostも利用できます。
2. 初回の読み込み後、共有メニューから「ホーム画面に追加」を選択します。
3. 人物を登録し、複数人をタップして花の変化を確認します。
4. アプリを閉じて再度開き、記録が残ることを確認します。
5. 一度オンラインでアプリを開いてから機内モードにし、ホーム画面から起動して日付変更・記録・再起動を確認します。
6. 5人で花が完成し、6・10・15人で色だけが変わること、同じ人物の再タップで取り消されることを確認します。

本実装の自動テストは日付・花・コメント判定とIndexedDBエミュレーションです。iPhone実機でのインストール、ストレージ保持、オフライン起動は実機確認が必要です。ブラウザデータ削除やOSによる保存領域削除で記録が消える可能性があります。現時点ではバックアップ・復元はありません。

Service Workerはアプリ資産を同一バージョンでキャッシュします。更新時は `CACHE` のバージョンを上げてください。005以降は新しい資産の取得が完了するとService Workerが有効になります。画面は強制再読み込みせず、次回の起動か設定の「最新版を読み込む」で新しいコードに切り替わります。人物記録はキャッシュとは別で、更新時に消去しません。

## 使い方

- 新規利用時は11枚の基本カードを用意します。不要なものは「…」から非表示にできます。既存利用者に基本カードを勝手に追加することはありません。
- カレンダーの日付から記録します。「今日の会話」は常に端末の今日を開きます。
- 人物ボタンは選択・解除するたびに自動保存します。1人物IDにつき1日1件です。
- 1人の相手はタップで選択・解除します。複数人のカードはタップで1人、選択後に＋－で調整、カード本体の再タップで全解除します。グループの人数には個別カードで選択した人を含めません。
- 人物・設定で名前、カテゴリ、上下の並び替え、非表示・再表示ができます。削除は論理削除（非表示）です。一覧から外したカードは過去日の入力画面でも非表示ですが、記録と花は保持します。必要なら設定の奥からカードを戻して編集できます。
- 利用開始日以降の0人の日は小さな双葉で表示し、否定的なメッセージは出しません。

## IndexedDB

データベース `talk-flower` / version 3（c013以降）。旧version 1/2は記録を維持して移行します。クラウド利用時は `talk-flower-user-<Auth UUID>` という別DBを使用します。

| ストア | 主キー | 内容 |
| --- | --- | --- |
| people | id | displayName, type, category, createdAt, sortOrder, isActive, firstTalkDate, lastTalkDate, totalTalkDays, currentMonthTalkDays, historyMonth |
| dailyLogs | id | date（端末のローカル日付 YYYY-MM-DD）, targetId, count, createdAt, recordType, personId（互換用） |
| settings | key | value。initialized, appVersion, appStartedAt, soundEnabled, starterCardsSeeded |

新規 `dailyLogs.id` は `date:targetId`（旧IDは保持）。`[date, targetId]` の複合ユニークインデックスで二重登録を防止し、人数変更は同じ行を更新、0人は削除します。date・targetIdにも検索インデックスがあります。旧personIdとそのインデックスは互換用に保持します。ログ変更と人物の履歴再集計を同一トランザクションで確定します。失敗時はロールバックします。複数タブの書き込みもIndexedDBのトランザクションにより直列化します。

`currentMonthTalkDays` は最終書き込み時点の月を `historyMonth` とともに保存するキャッシュです。コメント判定は保存済み集計値に頼らず、対象日より前のログから算出するため、月替わりや過去日の編集でも未来の履歴を参照しません。consecutiveDaysは未実装です。

保存対象は相手の名前・種類・関係カテゴリ・話した日・人数とID・時刻・並び順などの管理情報のみです。会話内容、会話時間、位置、電話番号、メール、音声、写真は取得しません。分析送信はありません。クラウドを有効にした場合のみSupabaseへ認証・同期の通信を行います。

## Supabaseを追加する場合

1. `db.js` の外に同期アダプターを追加し、ローカル書き込みを維持して未同期操作をキューに保存します。

5. IndexedDBのバージョンを上げ、既存データを維持するマイグレーションを追加します。

## 効果音（v1.1.0）

`js/sound.js` がWeb Audio APIの低めの正弦波で音を生成します。通常は0.32秒、5人目は3音が少しずつ上がる約1.2秒の開花音です。解除時は無音、6人目以降は通常音です。外部音声ファイルは使用しません。設定の「効果音 ON / OFF」は `settings.soundEnabled` に保存し、未設定時はONです。OFFにすると再生中の音も短くフェードアウトします。

iPhone向けに人物タップの同期処理内でAudioContextを作成・再開し、無音バッファを開始します。保存成功後に音を鳴らし、再生不可でも記録は継続します。実機では端末音量を調整し、Safari・ホーム画面起動・バックグラウンド復帰・オフライン・OFF設定の再起動後保持を確認してください。実機の音質・再生は未検証です。更新受信後はアプリの画面・タブをすべて閉じて開き直すと新しいキャッシュが有効になります。

## コメントの方針

会話の良し悪し・感情・相手への好意や感謝は推測しません。記録の追加、花の変化、前の記録からの間隔のみを表現します。5人目は個別履歴より「今日の花が咲きました 🌸」を優先します。6人目以降は花びらが増える表現を使いません。人物別の回数は表示しません。

## バージョン管理

アプリの連番は001から開始します。設定画面と `js/version.js` で確認できます。変更内容は `CHANGELOG.md` に記載し、完成版には `release-001` 形式のGitタグと番号付きソースZIPを残します。現在はc016、次回はc017です。Sites側の自動バージョン番号とは別管理です。

## 002：季節と双葉

`js/seasons.js` の12か月分の文章を編集できます。トップの説明は設定画面へ移動しました。5週の月を標準文字サイズで縦画面に収めるためにヘッダーと余白を圧縮し、花の描画サイズは維持します。6週の月、小さな表示領域、拡大文字では必要に応じて縦スクロールできます。

`settings.appStartedAt` はローカル日付のYYYY-MM-DD文字列です。初回画面の表示前に、トランザクション内で未設定の場合だけ保存します。001以前からの移行では、現存する人物の作成日・ログ作成日・記録日と今日の最も古い日付を採用します（正確な初回起動日の情報は旧版にないため推定）。情報がなければ移行日を採用します。以後の起動・記録編集では変更しません。

003以降は会話記録を優先し、1人以上なら日付にかかわらず人数に応じた花を表示します。0人の場合のみ、開始日前は空欄、開始日以降・未来日は双葉を表示します。

## 004：かんたんな人物追加

設定の「人物を追加」は候補ボタン＋名前だけの入力画面を開きます。候補のタップ・名前の追加はその場で自動保存され、続けて追加できます。「完了」で人物一覧へ戻ります。自由入力のカテゴリはその他です。カテゴリなどの詳細は人物一覧の「編集」で変更します。同名の人物は重複追加せず、非表示の場合は既存IDと記録を維持して再表示します。

## 005：更新の読み込み

10月の花は金木犀です。10/1に1人記録した場合も、未来日を理由に双葉へ戻すことはありません。旧版が残る場合は設定画面のバージョンを確認してください。005以降は「最新版を読み込む」で更新を確認し、記録を維持して再読み込みできます。旧版からの初回移行はオンラインで開いた後、アプリを閉じて開き直してください。ブラウザのデータ削除は必要ありません。端末内の実データや表示状態は開発環境から確認できません。

## 006：記録できる日付

今日と過去日は入力可能です。利用開始日前でも1人以上の記録があれば通常の花、0人なら空欄です。開始日以降の0人は双葉です。明日以降の日付はタップすると理由を表示し、入力しません。直接の日付URLとIndexedDB書き込み処理も未来日を拒否します。端末のローカル日付で判定します。旧版で作成した未来日の記録は削除せず花として保持し、その日以降に編集できます。

## 007：登録画面・3列・並び替え

初回も候補ボタンと名前入力の登録画面を使い、追加するたびに保存します。「完了」でカレンダーへ進みます。会話入力は3列です。設定の人物一覧の左のつまみを指やマウスでドラッグすると並び替えでき、離すと保存します。画面端では自動スクロールします。上下ボタンでも操作できます。並び順だけを最新の人物データに保存するため、人物名・非表示設定・過去の記録は変えません。iPhone実機のドラッグ操作は未検証です。

## 008：設定は直接ボタン画面へ

「人物・設定」を押すと、登録済み人物の3列ボタンと追加候補、名前入力が同じ画面に表示されます。登録済みの名前ボタンは編集、未登録の候補ボタンは即時追加です。各人物の下のつまみをドラッグして並び替えます。つまみにフォーカスして矢印キーでも移動できます。会話入力の3列にも同じ順序を反映します。

## 009：相手とグループ

設定は従来どおり3列カードです。1人の相手は淡いクリーム、複数人は淡い緑。種類の文字はカードに常設しません。「…」で種類・名前・非表示を設定します。名前の自由入力時のみ種類を尋ね、キャンセル時は保存しません。新規カードのtypeは選択値を使い、名前で固定しません。

人数合計は `records.js` の `totalTalkCount()` を共用します。例：妻1＋佐藤さん1＋同僚3＝5人。1日・1カードにつき1行で、groupの＋－は同じ行のcountを更新します。本文ボタンと人数操作ボタンはDOM上の兄弟で、人数操作は伝播も停止します。花は5人で完成し、6人以上で色が変化します。人数を増やした時だけ効果音、5人になった時は開花音を使用します。カードの履歴は人数でなく記録した日数を集計します。

既存typeなしカードはpersonとして移行し、全ての旧ログにtargetId（旧personId）、count=1を補います。typeのあるカードは種類を変更しません。ID、createdAt、sortOrder、isActive、settingsは保持します。移行はIndexedDBのupgradeトランザクションで行い、失敗時はロールバックします。過去に複数人記録があるカードを1人へ変更しても、過去のcountを1へ減らしません。その過去の記録はグループ表示・調整を保ち、新規日付の記録は現在の種類を使用します。既存の1人の記録は種類をグループへ変更すると、そのまま人数を増やせます。

`cards.js`：入力カードと設定カードのHTML、`records.js`：人数・種類・共通集計。`db.js`：移行、基本カードの一度だけの作成、人数変更、履歴更新。実行時ライブラリは追加していません。

初回画面だけ確認する場合は、別ブラウザでURLを開くと現在のブラウザの記録を消さずに試せます。アプリ内に全消去機能は実装していません。

## 010：カードを一覧から外す

「…」の「一覧から外す」はpeople.isActive=falseのみを書き込みます。今後は過去日を開いた場合も含め、入力画面と設定の通常カードには表示しません。過去のdailyLogsと人数・花は変更しません。花の合計は非表示カードも含む全ログのcountから計算します。設定の奥の「一覧から外したカード」を開くと、同じID・履歴のまま復帰できます。完全削除は実装していません。

## 011：月ごとの花

梅の丸い花弁、水仙の副花冠、桜の切れ込み、開くチューリップ、青と白のネモフィラ、小花が集まる紫陽花、漏斗形の朝顔、多数の黄色い花弁のひまわり、細い花弁のコスモス、小花の房の金木犀、重なる花弁の菊、色づく苞葉のポインセチアを描き分けました。カレンダーと入力はサイズのみ違う同じSVGです。保存済み人数をそのまま新しい意匠で表示し、データ移行・初期化はしません。

## 012：カレンダーの花を拡大

カレンダーは共通SVGの茎・葉のグループを非表示にし、花種別viewBoxで花の部分を拡大します。入力画面は茎・葉つきの全体表示を維持します。0人の双葉とポインセチアの苞葉は維持します。紫陽花は小花を密に配置し、完成時に丸い房になります。


## c013：クラウド同期の導入と現在の確認範囲

接続設定なしでもこれまでどおり利用できます。設定の「クラウド同期」は接続準備中と表示します。認証方式はメールOTPです。決済や有料制限は未実装で、設定したプロジェクトの認証済みユーザーは同期を利用できます。一般公開前に下記チェックを完了してください。

33件の自動テストが通過しています。自動テストではPGlite（実際のPostgreSQLエンジン）にテストユーザーA/Bを作成し、schema.sqlを適用してRLS・外部キー・LWWを検証します。これは実際のSupabase AuthアカウントやREST経路の検証とは別です。Supabase接続設定がない状態で、実環境A/Bアカウント作成、メール配信、REST漏洩テスト、iPhone/iPadの同期を完了したとは扱いません。

### Dashboardでの設定

1. Supabaseでこのアプリ専用プロジェクトを作成します。既存の別アプリのテーブルへSQLを適用しないでください。リージョンを選び、DBパスワードをパスワードマネージャーで管理します。
2. Authentication → Providers → Emailを有効にし、メール確認を有効にします。匿名サインインは使用しません。
3. Authentication → Email Templates → Magic Linkのテンプレートで `{{ .Token }}` を表示するように設定します。リンクではなくメール本文の確認コードをPWAへ入力します。コードの有効期限・再送制限を設定します。
4. AuthenticationのSite URLを配信するHTTPS URLにします。不要なRedirect URLを登録せず、本番で広いワイルドカードを使用しません。本アプリは認証URLフラグメントを処理しません。
5. 一般公開用にはSMTP、送信元ドメイン、レート制限、必要なボット対策を設定します。標準メール送信環境の制限を確認します。現在のフロントにCAPTCHA入力は未実装です。
6. SQL Editorで次項のSQLを実行します。
7. Project URLとpublishable key（または従来のanonキー）を取得します。service_roleキーは使用しません。

### 本番に適用するSQL

- `supabase/schema.sql`：最初に一度実行します。テーブル、制約、RLS、権限、ポリシー、同期関数を**同じトランザクション**で作成します。途中にRLSなしで公開される状態を作りません。
- `supabase/indexes.sql`：次に実行します。
- `supabase/rls.sql`：ポリシーの参照用コピーです。schema.sqlに含まれるため重複実行しません。
- `supabase/seed.sql`：共有データは挿入しません。新規アカウントの初期カードは、初回同期先が空の場合だけ本人のデータとして生成します。

schema.sqlは新規専用プロジェクト用です。既存テーブルを消す処理はありません。再適用はエラーになるため、今後の変更は別のmigrationとして作成してください。

`daily_logs`は `(user_id,date,target_id)` が一意です。`(user_id,target_id)` → `people(user_id,id)` の複合外部キーにより、他人の人物IDは参照できません。人物の通常操作はis_activeのみ変更します。会話の取消はdeleted_at付きの行を残して同期し、count自体は1以上を維持します。物理DELETE権限はクライアントに与えていません。人物を非表示にしても過去ログは変わりません。

### 環境変数と公開される情報

`.env.example`を`.env.local`としてコピーし、以下だけ設定します。

```dotenv
SUPABASE_URL=https://your-project.supabase.co
SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

`npm run build` / `npm run dev` は許可した2値だけを `js/cloud/config.js` に生成します。`.env`・`.env.local`・`.env.security`・生成済みconfig・vendorはGit対象外です。配信には `dist/` のみを使います。開発サーバーも.envやSQL、テスト、ソース設定を配信しません。

| 情報 | 扱い |
| --- | --- |
| Supabase URL / publishable・anonキー | ブラウザ・配信JS・PWAキャッシュから見える公開情報。RLSがデータを保護します |
| Auth access token / refresh token | ログインした本人のセッション資格情報。公式SDKがこのブラウザのlocalStorageに保持します。ソースへ埋め込まず、ログへ出しません。他人に渡さないでください |
| ログイン用メール | Supabase Authが保持します。public.profiles / people / daily_logs / settingsへコピーしません |
| service_role / secret key / DBパスワード / management token / Stripe secret | フロントでは使用しません。Git、配信物、IndexedDB、localStorageに設定値として置きません。将来必要ならサーバー側の秘密ストアのみ |

ビルドはsecretキーやservice_role JWTを公開キーとして受け付けません。ただしビルド検査に頼らず、配信前に最終成果物も確認してください。CSPで同一配信元のスクリプトだけ許可し、クラウド通信先を設定済みのSupabaseに限定します。SPAのセッション保持はHttpOnly Cookie方式ではなく、XSSが起きればセッショントークンもリスクにさらされます。外部スクリプトを追加しない、文字列をHTMLエスケープする、依存パッケージを監査する方針を維持します。

### オフライン・競合・再試行

- 人物タップはIndexedDBへ保存し、UIと音を更新します。通信待ちはしません。
- アカウント別DBの `syncState` に `{id,store,record,deleted,updated_at,mutation_id,sync_status}` を同じトランザクションで保存します。途中で落ちてもレコードとキューがずれません。
- オンライン復帰、前面復帰、前面表示中の30秒間隔、操作後、手動同期で再送・受信します。失敗時は最大60秒間隔まで遅延して再試行します。PWAが完全に閉じている間のバックグラウンド通信は保証しません。次回起動時に再開します。
- 人物→会話→設定の順で送信します。受信は500件ずつ、削除情報を含めて照合します。個人用MVP向けの全件照合です。大規模データにはrevision/cursor方式へ拡張してください。
- `resolveConflict()` はupdated_atが新しい方を採用します。同時刻はmutation_idで決定します。DB側も同期関数の `ON CONFLICT ... WHERE` で**原子的**に判定します。古いオフライン端末が新しい記録を無条件に上書きしません。
- 時刻は端末依存です。同一レコードの端末内連続更新は時刻を単調増加させますが、端末時計の大幅なずれを完全に解決するものではありません。将来server revision・フィールドマージ・競合通知を追加できます。
- 送信中にさらに編集した場合、古い応答で新しいpendingを消しません。
- 物理削除ではなくtombstoneを照合し、取り消した会話の復活を防ぎます。
- 同期対象設定は `appStartedAt / soundEnabled / theme` の許可リストです。認証情報・同期有効化・アプリ版・端末管理情報は同期しません。関係カテゴリは当面端末内のみで、新端末では「その他」です。

## c020 初回画面の自動引き継ぎ

「はじめて使う方」と「すでに利用している方」を同じ色・見出しサイズ・ボタンで併記します。はじめての方は人物登録へ、既存利用の方はGoogleログイン→既存Supabaseデータの取得→アカウント別IndexedDBへ反映→同期有効化→カレンダーへ進みます。通常の設定画面のGoogleログインと手動移行は従来どおりです。

- `js/cloud/restore.js`: 認証済みユーザーの検証、全ページ取得、ローカル反映を分離。Google Driveは使っていません。SQL・データ形式は変更していません。
- ローカルに保存する復元意図は30分有効の時刻のみ。認証情報ではなく、本人確認はSupabase getUserとRLSで行います。成功/キャンセル/失敗で意図を消去します。
- 全ストアの取得完了後に一括反映。認証/取得中は初回登録UIを表示しません。クラウドが空の場合は新規の人物登録へ進みます。
- ログイン前のDBはそのまま保持し、自動アップロードしません。同じアカウントDBに未同期レコードがあれば、反映トランザクション内で検出して停止します。ローカルを削除せず、状態確認のため戻れます。通常同期のLWWは変更していません。
- すでにあるprofiles以外にユーザーDBや課金テーブルは追加しません。将来のプラン判定はfetchRestoreSnapshotの本人確認後・データ取得前、および通常同期のサーバー側アクセス制御へ追加します。ブラウザのプランフラグで認可しないでください。
- Auth状態/Google認証はclient.jsとgoogle-auth.js、復元はrestore.js、継続同期はsync.js、画面状態はui.jsです。

検証: 自動テスト41件。テスト専用ブラウザとモック認証/クラウドで、通常/standaloneフラグ、読み込み表示、自動有効化、再読み込みの重複防止、空クラウド、取得失敗を確認。実際のGoogle認証とiPhoneホーム画面からの復帰は実端末で要確認です。OAuthが別ブラウザで開く場合、そのブラウザとホーム画面版の保存領域は自動共有されません。
